# Мова запитів 1С (SDBL) — довідник структурних правил

## Статус і призначення цього документа

Це **не** повний формальний опис мови запитів 1С — такий є в офіційній книзі
"Язык запросов «1С:Предприятия 8»" (Е. Ю. Хрусталева, вид. 1С-Паблишинг, серія
«1С:Библиотека разработчика»); якщо є легальний доступ до неї — вона авторитетніша
за цей файл у будь-якому спірному питанні.

Порядок секцій у розділі 1 нижче звірено з цією книгою (гл. 1, «Синтаксис
текста запроса», рис. 1.13 «Секции запроса», а також приклад пакетного запиту
з тимчасовою таблицею у гл. 2) — розбіжностей не знайдено. Правило зі
розділу 3 (які ключові слова ніколи не можуть з'явитись усередині виразу) у
книзі окремо явно не сформульоване — це наш власний висновок з емпіричної
перевірки парсера на корпусі реальних запитів.

Цей документ фіксує **структурні правила запиту**, які:
- підтверджені емпірично — прогоном через `sdblParser.ts` і звіркою на золотому
  корпусі з 1976 реальних запитів (`test/fixtures/corpus/golden.jsonl`,
  `corpusRegression.test.ts`) та точковими MCP-пробами на живому 1С (сліди цього —
  коментарі `MCP-проба`/`validate_query` у коді парсера);
- мають пряме відношення до **валідації тексту запиту при ручному редагуванні**
  (панель «Текст запроса» v2) — саме тут користувач може ввести синтаксично
  некоректний текст, і важливо, щоб парсер це помітив, а не мовчки прийняв.

Оновлюйте цей файл, коли аудит чи ручне тестування виявляють нове структурне
правило (за тим самим принципом, що й тести в `test/unit/validateBatch.test.ts`).

## 1. Структура одного запиту (без пакету)

Секції йдуть у ЦЬОМУ порядку; усі, крім `ВЫБРАТЬ`/`ИЗ`-джерела, необов'язкові:

```
ВЫБРАТЬ [ПЕРВЫЕ N] [РАЗЛИЧНЫЕ] <список полів>
    [ПОМЕСТИТЬ <ИмяВТ> | ДОБАВИТЬ <ИмяВТ>]
[ИЗ <источники (с СОЕДИНЕНИЕ ... ПО <условие>)>]
[ГДЕ <условия>]
[СГРУППИРОВАТЬ ПО <поля>]
[ИМЕЮЩИЕ <условия>]
[ОБЪЕДИНИТЬ [ВСЕ] <следующий ВЫБРАТЬ ...>]   -- ветви объединения на одном уровне
[УПОРЯДОЧИТЬ ПО <поля>] [АВТОУПОРЯДОЧИВАНИЕ]
[ИТОГИ <агрегаты> ПО <поля>]
[ИНДЕКСИРОВАТЬ ПО <поля>]
[ДЛЯ ИЗМЕНЕНИЯ [<таблицы>]]
```

`ИЗ` формально необов'язковий — 1С допускає запит-константу без джерела
(`ВЫБРАТЬ &Параметр КАК Поле`), типово для формування тимчасової таблиці з
констант/параметрів.

`ПОМЕСТИТЬ`/`ДОБАВИТЬ` завжди стоять МІЖ списком полів і `ИЗ` — ніколи після
`ИЗ`, `ГДЕ` чи будь-якої пізнішої секції.

## 2. Пакет запитів

Кілька запитів (кожен — повна структура з п.1), розділених `;`. Канонічний
роздільник, який друкує конструктор 1С, — `;` + порожній рядок + рядок з 80+
символів `/` (коментар-розділювач); але сам по собі голий `;` теж є валідним
роздільником.

**Що реально повертає `Запрос.Выполнить()`** — це результат **останнього**
запиту пакету. Всі попередні запити, як правило, створюють тимчасові таблиці
(`ПОМЕСТИТЬ`/`ДОБАВИТЬ`) для використання наступними. Панель «Структура» (це
розширення) саме тому розділяє «Результат» (останній запит) і «Временные
таблицы» (усе до нього) — див. `QueryAnalysisService.analyze()`.

## 3. Головне структурне правило (джерело майже всіх знайдених багів)

**Жодне з цих ключових слів НІКОЛИ не може легітимно з'явитись як «голий»
токен усередині виразу/умови/списку полів:**

```
ВЫБРАТЬ  ИЗ  ПОМЕСТИТЬ  ДОБАВИТЬ  ГДЕ  СГРУППИРОВАТЬ  ИМЕЮЩИЕ
ОБЪЕДИНИТЬ  УПОРЯДОЧИТЬ  ИТОГИ  ИНДЕКСИРОВАТЬ  ДЛЯ
```

Єдиний легітимний випадок, коли одне з цих слів зустрічається "не як
роздільник секції" — коли воно є ІМЕНЕМ поля/псевдоніма таблиці в
крапковому шляху (`Итоги.Ссылка`, де `Итоги` — назва довідника/псевдонім,
а не ключове слово; парсер розрізняє це за наявністю `.` одразу після).

### Чому це важливо

`sdblParser.ts` — рукописний recursive-descent парсер. У багатьох місцях він
читає "сирі" токени до якогось стоп-слова (список полів, умова `ГДЕ`, умова
`ПО` в `JOIN`, `УПОРЯДОЧИТЬ ПО`, `ИТОГИ` тощо) і, якщо не розпізнає структуру
однозначно, зберігає прочитане як «довільний вираз» (`custom: true, expression:
<сирий текст>`) — це навмисний і потрібний механізм для довільних виразів 1С.

Проблема: кожне таке місце тримає **свій власний** список стоп-слів, і донедавна
жоден з них не містив повного переліку з цього розділу. Якщо користувач руками
вводить помилку — структурне ключове слово опиняється не там, де парсер його
очікує (типова причина: неправильний порядок секцій при ручному редагуванні,
або скопійований шматок іншого запиту) — парсер **мовчки проковтує все до кінця
тексту** як один "довільний вираз", включно з реальною секцією `ИЗ`, яка після
цього просто зникає з моделі без жодної помилки.

### Де це перевіряється в коді (станом на 2026-09)

| Секція | Стоп-набір | Рядок (`sdblParser.ts`) |
|---|---|---|
| Список полів `ВЫБРАТЬ` | inline-перелік у `parseOneField` | ~1274, ~1284 |
| `ГДЕ` | `WHERE_STOP` | ~2583 |
| `ИМЕЮЩИЕ` | `HAVING_STOP` | ~2611 |
| Умова `ПО` в `JOIN` | `JOIN_COND_STOP` | ~1921 |
| `СГРУППИРОВАТЬ ПО` / `УПОРЯДОЧИТЬ ПО` / `ИНДЕКСИРОВАТЬ ПО` / `ДЛЯ ИЗМЕНЕНИЯ` | `SECTION_KEYWORDS` / `isSectionKeyword` | ~4199 |
| `ИТОГИ <агрегат>` (до `ПО`) | inline-перелік у `parseTotalAggregate` | ~3782 |

Усі ці набори МАЮТЬ включати `ПОМЕСТИТЬ`/`ДОБАВИТЬ`/`ИЗ` (і там, де це
структурно можливо — `ОБЪЕДИНИТЬ`/`ВЫБРАТЬ`). Regression-тести на цей клас
багу — `test/unit/validateBatch.test.ts`, блок
`«структурные ключевые слова внутри «сырых» выражений»`.

### Друга лінія захисту: перевірка "чи дійшли до кінця"

Окремо від стоп-слів кожної секції, `parseDocumentInner` (верхній рівень одного
`;`-блоку/учасника об'єднання) перевіряє, що курсор парсера дійшов рівно до
кінця тексту цього блоку. Якщо після успішного розбору залишились нерозпізнані
токени — це гарантована синтаксична помилка, а не "ну і нехай". Це ловить
випадки, коли стоп-слово в конкретній секції ще не додане (сирий текст лишається
НЕ проковтнутим, а просто "висить" після кінця розбору) — на відміну від
випадків з дірою в стоп-наборі, де текст проковтується ПОВНІСТЮ (і ця перевірка
тоді безсила — рятує лише правильний стоп-набір).

## 4. Типові помилки при ручному редагуванні (і як їх розпізнати)

- **Секція не на своєму місці** (`ГДЕ` до `ПОМЕСТИТЬ`, `УПОРЯДОЧИТЬ` до `ГДЕ`
  тощо) — найчастіша причина після copy-paste шматка іншого запиту. Тепер дає
  чітку помилку розбору замість "✓ Синтаксис корректен".
- **Зайвий текст після псевдоніма поля** (`... КАК Поле мусор ще`) — теж дає
  помилку "после конца запроса остались нераспознанные данные".
- **Порожній/пробільний текст** — технічно валідний "порожній пакет" на рівні
  парсера, але панель «Текст запроса» v2 окремо блокує «Применить» на ньому
  (`ConstructorView.handleApplyQueryEdit`) — інакше застосування порожнього
  тексту тихо стирало б усю модель конструктора.

- Повний перелік функцій/операторів виразів (`СУММА`, `ВЫБОР…КОНЕЦ`,

- Віртуальні таблиці регістрів (`Обороты`, `ОстаткиИОбороты` тощо) і їхні

  профільні тести (`accountingVirtualTables.test.ts`, `accumVirtualFields.test.ts`).
- Три місця, позначені попереднім аудитом як "потребують подальшого
  дослідження, не підтверджено" (можлива, але не доведена вразливість того ж
  класу): проекції табличних частин з розбалансованими дужками,
  групи `ИТОГИ` в дужках, `ПЕРИОДАМИ(...)`.
