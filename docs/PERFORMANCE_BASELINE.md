# Performance baseline (PR-03, ТЗ v2.1 §44/§54 P0.3)

Статус: **baseline, не архітектурне рішення**. ТЗ §44 (LOCKED) вимагає для кожного
performance-рішення: метрика → baseline → representative workload → user impact →
budget → decision gate → regression check. Ця ітерація дає перші п'ять пунктів
(факти); **decision gate тут навмисно не спрацьовує** — жодного бюджету/порогу ще
не визначено (§23/§44 забороняють вигадувати довільні пороги без evidence), і
жодне з виміряних чисел не виглядає як очевидна проблема. Якщо колись з'явиться
конкретна скарга/вимога щодо продуктивності — цей документ дає точку відліку
"було", без якої "стало краще/гірше" не можна перевірити.

Скрипт: [`bench/metadataPerf.ts`](../bench/metadataPerf.ts) (`npx tsx --expose-gc
bench/metadataPerf.ts`). Живе поза production runtime (ТЗ §45) — нічого з
`src/extension`/`src/webview` його не імпортує.

## Workload

`test/fixtures/corpus/metadata/cf/` — реальна, представницька конфігурація
**БиблиотекаСтандартныхПодсистем** (БСП), 558 об'єктів метаданих (713 таблиц після
розгортання регістрів/віртуальних таблиць), вже закомічена як фікстура для
`corpusRegression.test.ts`. `test/fixtures/corpus/golden.jsonl` — 1976 реальних
запитів з тієї ж конфігурації.

## Результати (3 прогони, 2026-09-04, Node v25.8.2, M-серії Mac)

| Категорія | Результат | Варіативність |
|---|---|---|
| **Cold build (XML → YAML)** | **не виміряно** | У репозиторії немає реального XML-джерела (`CONFIG_DIR=src/cf` за замовчуванням не існує на чистому checkout — див. `docs/corpus-testing.md`). Єдина XML-фікстура — 2 об'єкти, вимір на ній був би хибною репрезентативністю. Потрібен зовнішній/ручний замір на реальному вивантаженні. |

| **Warm load** (JSON model-cache вже є) | ~9.5-10.2 мс | стабільно, ~25-30× швидше cold |
| **`rebuildModelCache`** (шлях `refreshCache`) | ~245-255 мс | стабільно, збігається з cold-from-YAML (очікувано — той самий повний розбір YAML) |

## Extension Host blocking (ТЗ §43)

Не вимірювалось окремим інструментом — встановлено прямим читанням коду:
`loadMetadata` (`src/extension/panel.ts:45`) позначена `async`, але **не містить
жодного `await` у власному тілі** — весь шлях (`parseConfiguration`,
`loadMetadataCached`, `fs.readFileSync`/`readdirSync`) синхронний. Це означає:
числа "Cold-from-YAML"/"Warm load"/"rebuildModelCache" вище **є** тривалістю
блокування Extension Host — виклик виконується в одному тіку до повернення в
event loop. Той самий висновок стосується `refreshCache`-обробника
(`panel.ts:167-190`).

## Decision gate (навмисно: без рішення)

- ~250-290 мс блокування Extension Host на кожному холодному відкритті
  конструктора (і на кожному «Обновить кэш») — помітно, але без визначеного
  бюджету "прийнятно/неприйнятно" робити висновок передчасно (ТЗ §44: жодних
  універсальних довільних відсотків).
- 563 КіБ WebView payload — для одноразового `postMessage` при відкритті панелі
  це не виглядає проблемним, але формального бюджету теж немає.
- **Жодної зміни коду в цій ітерації не зроблено** — §43/§53 ТЗ прямо застерігають:
  Worker Thread/Child Process — це рішення, яке приймається ЛИШЕ якщо бюджет
  порушено і порівняння підходів це виправдовує, не заздалегідь.

## Regression check

Наступний раз, коли хтось міняє `parseConfiguration`/`loadMetadataCached`/
`sdblParser`/`sdblGenerator` і підозрює вплив на продуктивність — перезапустити
`bench/metadataPerf.ts` і порівняти з таблицею вище. Це не CI-gate (жодного
порогу для провалу тесту не встановлено — навмисно, немає evidence для
конкретного числа), а довідкова точка порівняння.

## PR-09: New snapshot (PR-08) vs існуючий model-cache.json

ТЗ §55 P1.3 вимагає performance comparison нового snapshot-backend проти
поточного production-шляху. Обидві сторони виміряні на ОДНІЙ і тій самій вже
побудованій моделі (`loadMetadataFromYaml`, той самий 558-об'єктний/713-табличний
БСП-воркload з розділу вище) — різниця нижче це різниця саме в commit/read I/O,
не в конверсії YAML→`MetaTable[]` (та не змінюється PR-08/09).

| Категорія | Результат |
|---|---|
| Снимок: commit (staged-build + ownership-marker + rename) | ~5.6 мс |
| Снимок: warm read (`readMetadataSnapshot`) | ~5.1 мс |
| Для порівняння: існуючий production warm load (`loadMetadataCached`, розділ 2) | ~9.5-10.3 мс |

Warm read нового снимка вимірюється швидшим за існуючий production warm load
(приблизно вдвічі) — ймовірне пояснення: `loadMetadataCached` перед читанням
кешу рекурсивно сканує YAML-каталог на найновіший mtime (перевірка свіжості),
тоді як `readMetadataSnapshot` просто читає вже закоммічений JSON-файл без
такої перевірки. **Це спостереження, не архітектурне рішення** — воно НЕ
враховує вартість freshness-перевірки, якої в снимка поки що взагалі немає
(§54 P1.2 прототип навмисно її не реалізує), і не є доказом, що снимок-бекенд
"кращий" в продакшн-сценарії. Decision gate для PR-10 (Production Metadata
Switch) залишається невизначеним навмисно, як і в розділі вище.

Скрипт: те саме `bench/metadataPerf.ts` (розділ 7, доданий цим PR).

Уточнення: замір вище зроблений ДО того, як `buildMetadataSnapshotFromXml` став
дійсно прямим (PR-08 completion, див. нижче) — тут `commitMetadataSnapshot`
викликався напряму над вже готовою моделлю (`loadMetadataFromYaml`), тобто
вимірювалась лише вартість commit/read самого JSON-файлу, а не повний шлях
XML → модель.

## PR-08 completion: заміри на реальній зовнішній конфігурації (direct XML-шлях)

Після того як `buildMetadataSnapshotFromXml` став дійсно прямим (парсить XML →
модель → JSON, зовсім без YAML-прошарку — див. KNOWN_ISSUES.md/git history
коміт "PR-08 completion"), з'явився сенс порівняти ПОВНИЙ холодний шлях
(XML → готова модель) старого і нового підходу, а не тільки commit/read JSON.

БСП-фікстура (558 об'єктів) для цього не підходить — у репозиторії немає її
сирого XML (тільки вже розібраний YAML, див. `docs/corpus-testing.md`).
Тому замір зроблено на РЕАЛЬНІЙ зовнішній конфігурації користувача — приватні
бізнес-дані, **не закомічені в репозиторій і не додані як фікстура** (лише
результат заміру документується тут). Масштаб: 1422 XML-об'єкти → 2610 таблиць
після розгортання регістрів/віртуальних таблиць (значно більше за 558/713
БСП-фікстуру, тобто це не менш представницький воркload).

| Категорія | Existing YAML-шлях (`parseConfiguration`+`loadMetadataCached`) | Direct-шлях (`buildMetadataSnapshotFromXml`) | Різниця |
|---|---|---|---|
| **Холодна збірка** (XML → готова модель) | ~2915 мс | **~1790 мс** | **у ~1.6 рази швидше** |
| Тепле читання (кеш/знімок вже є) | ~47 мс | ~45 мс | практично однаково |
| Кількість таблиць у результаті | 2610 | 2610 | **ідентично** |

Ймовірне пояснення прискорення: existing-шлях пише 1422 окремих YAML-файли на
диск, потім читає індекс і всі 1422 файли назад; direct-шлях тримає розібрані
об'єкти в пам'яті між парсингом XML і одним записом JSON — без проміжного
диска. Кількість таблиць співпала побайтово в обох шляхах на цій конфігурації —
додатковий, незалежний від `test/fixtures` доказ, що прямий шлях не губить і
не змінює дані (доповнює `snapshotBuilder.test.ts`/`snapshotValidation.test.ts`).

**Це вже конкретна evidence-based підстава для майбутнього рішення по PR-10**
(Production Metadata Switch) — на відміну від попереднього розділу, тут
порівнюється ПОВНИЙ шлях (не лише commit/read) на представницькому за розміром
реальному воркloadі. Сам decision gate (чи перемикати продакшн) залишається
окремим рішенням — це вимір, не архітектурне рішення (ТЗ §44).

Замір не автоматизований у `bench/metadataPerf.ts` (потребує зовнішньої, не
закомієченої конфігурації) — разовий скрипт, запущений локально, результат
задокументований тут вручну.
