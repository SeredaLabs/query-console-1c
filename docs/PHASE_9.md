# Фаза 9. Текст запроса v2 и укрепление ядра парсера

← [Дорожная карта](ROADMAP.md)

✅ Готово (2026-09-03). Опирается на двунаправленное ядро Фаз 6–8. Три независимых
направления одной итерации: (1) новый режим окна «Текст запроса» — **opt-in**, не меняет
поведение по умолчанию; (2) укрепление парсера против структурных ошибок, которые раньше
молча проглатывались как «сырое» выражение; (3) доработки семантического валидатора.
Золотой оракул и регрессия корпуса 1976 запросов — байт-в-байт без изменений.

## Подфаза 9.1. Диалог «Текст запроса» v2 — opt-in

Спек: [`2026-09-02-query-text-dialog-v2-design.md`](superpowers/specs/2026-09-02-query-text-dialog-v2-design.md).

**Что было не так.** Старое окно «Текст запроса» — голое текстовое поле без номеров
строк, поиска, форматирования, проверки на лету или обзора структуры пакета.

**Итог.** Новый режим окна за настройкой `queryConsole.queryTextEditorV2` (`boolean`,
по умолчанию `false` — включается по потребности пользователя, не становится дефолтом
только по факту публикации).

- **Редактор**: CodeMirror с расширенными возможностями (номера строк, подсветка активной
  строки, парные скобки, folding, поиск/замена Ctrl/Cmd+F/H) поверх прежнего `CodeEditor`.
- **Тулбар**: отменить/повторить, «Форматировать» (лексический pretty-printer —
  `queryTextFormatter.ts`, без построения `QueryModel`, откатывается одним `Undo`),
  «Проверить», переключатели панелей «Параметры»/«Структура», «Поиск».
- **Единый анализ**: `QueryAnalysisService.analyze()` (`queryAnalysisService.ts`) — и кнопка
  «Проверить», и фоновая проверка с дебаунсом 400мс, и статус-бар используют один и тот же
  вызов вокруг `tryOpenBatch`; ошибки анализа не блокируют редактирование (`try/catch`).
- **Панель «Структура»** (`QueryStructurePanel.tsx`): поля/источники/соединения/условия
  «Результата» и каждой временной таблицы, переход «клик → код» (best-effort поиск текста,
  ограниченный своим `;`-блоком пакета через `textRange`, иначе — по всему тексту).
- **Панель «Параметры»** (`QueryParametersPanel.tsx`): read-only список параметров запроса.
- **Защита от потери изменений**: единая точка закрытия для `×`/клика по фону/«Отмена» —
  если текст менялся с момента открытия, показывается диалог подтверждения вместо
  немедленного закрытия.

Файлы: `QueryTextDialog.tsx`, `QueryStructurePanel.tsx`, `QueryParametersPanel.tsx`,
`queryAnalysisService.ts`, `queryTextFormatter.ts`.

## Подфаза 9.2. Укрепление парсера: полнота стоп-слов и контроль недоразобранного текста

**Что было не так.** Многие границы парсера (список полей, `ГДЕ`/`ИМЕЮЩИЕ`, условие
соединения, `СГРУППИРОВАТЬ ПО`, `УПОРЯДОЧИТЬ ПО`, `ИНДЕКСИРОВАТЬ ПО`, `ДЛЯ ИЗМЕНЕНИЯ`,
агрегаты `ИТОГИ`) на неудаче разбора структуры молча сохраняют «сырой» срез текста как
`{custom: true, expression: …}` — намеренная лазейка для произвольных выражений 1С. Но
набор стоп-слов, на которых такой срез должен останавливаться, был для каждой границы
independently и не полностью перечислен: опечатка/неверная перестановка ключевого слова
(`ПОМЕСТИТЬ`/`ДОБАВИТЬ`/`ИЗ`/`ОБЪЕДИНИТЬ`) могла быть молча проглочена как часть «сырого»
выражения — в худшем случае целиком поглощая настоящий хвостовой `ИЗ <таблица>`, так что
таблица пропадала из разобранной модели, а запрос всё равно считался корректным.

**Итог.** Расширены стоп-слова `WHERE_STOP`, `HAVING_STOP`, `JOIN_COND_STOP`,
`SECTION_KEYWORDS` (общая константа для группировки/сортировки/индекса/блокировки) и
инлайн-стоп-условие `parseTotalAggregate` — 6 точек закрыто одним скоординированным
проходом. Дополнительно: верхнеуровневая проверка «весь ли ввод разобран» в
`parseDocumentInner` — после разбора члена объединения бросает ошибку, если курсор не
дошёл до конца текста (ловит НЕразобранный мусор; для случая, когда мусор был разобран,
но неверно — нужны были именно фиксы стоп-слов выше).

Новые тесты: `validateBatch.test.ts` — блок из 8 тестов (7 — каждый исправленный
уязвимый паттерн теперь даёт `ok:false`; 1 — те же 6 секций в легитимной форме остаются
`ok:true`, guard от ложных срабатываний). Полный корпус (1976 запросов) и e2e — без
изменений.

Справочный документ: [`1c-query-language.md`](1c-query-language.md) — структурные правила
SDBL (порядок секций, инвариант «структурные ключевые слова никогда не встречаются голыми
внутри выражения» с таблицей исправленных мест, типичные ошибки ручного редактирования).

## Подфаза 9.3. Семантический валидатор: колонки ОБЪЕДИНЕНИЯ + архитектурный фикс

**Что было не так.** `validateBatchSemantics` в самом начале делала `if (!resolver) return
[]`, из-за чего резолвер-независимые проверки (дубль псевдонима) пропускались всегда,
когда метаданные ещё не загружены (например, до прогрева кэша конструктора) — не
архитектурно оправданный побочный эффект, а баг.

**Итог.** Гейт по резолверу перенесён внутрь `checkTable` (единственная проверка, которой
он действительно нужен). Добавлена новая независимая от резолвера проверка
`checkUnionColumnCount` — использует `orderedSelectElements` (`unionModel.ts`, та же
функция, что уже считает «колонки» для генератора) и даёт ошибку при несовпадении числа
колонок между участниками ОБЪЕДИНЕНИЯ.

## Подфаза 9.4. Ещё три критических бага ядра (найдены адверсарной перепроверкой)

Перед применением фиксов 9.2 каждое предложенное решение было реально применено и
прогнано через полный гейт (`typecheck` + весь `test:unit`, включая корпус 1976
запросов) в изолированном git worktree — только после подтверждения безопасности
изменения перенесены в основной код.

- **Лексер молча принимал незакрытый строковый/дата-литерал** вместо ошибки
  (`sdblLexer.ts`): сканер строки выходил из цикла по EOF, не проверив, что реально
  дошёл до закрывающей кавычки; сканер даты не проверял это вовсе. Экранирование `""`
  внутри строк не затронуто. Исправлено, тест — `sdblLexer.literals.test.ts`.
- **Не было ограничения глубины рекурсии подзапросов** (`ИЗ (…)`/`В (…)`) —
  патологически глубокая вложенность могла уронить процесс по памяти (`heap out of
  memory`, не перехватывается никаким `try/catch`), а не просто бросить обычную
  ошибку: каждый уровень заново токенизирует и разбирает почти весь остаток текста.
  Максимум по золотому корпусу — 3; лимит поставлен на 32 отдельным счётчиком (не
  путать с `subquerySourceDepth` — тот про семантику `СГРУППИРОВАТЬ ПО`, не про
  безопасность стека). Тест — `validateBatch.test.ts`.
- **`parseTabColumn` (7-е место того же класса, что и в 9.2)** — выражение-колонка в
  проекции табличной части (`Т.ТЧ.(…)`) читалось сырым срезом без стоп-слов; `ИЗ`
  внутри нее молча становилось частью «произвольного» выражения вместо синтаксической
  ошибки. Найдено адверсарной перепроверкой уже закрытого пункта 9.2, не первым
  проходом аудита. Исправлено тем же способом (стоп-слово `SECTION_KEYWORDS`).

Полный гейт после всех трёх фиксов вместе: **59 файлов / 1401 тест**, золотой
оракул/регрессия корпуса — байт-в-байт без изменений.

## Подфаза 9.6. Лінтер антипатернів запиту (advisory-попередження)

**Що було не так.** `semanticValidator.ts` перевіряє лише коректність (блокуючі
помилки) — жодної перевірки якості/ефективності запиту не було. Порівняння з
`bsl-language-server` (зовнішній інструмент екосистеми 1С) показало клас діагностик,
якого нам бракує: `FullOuterJoinQuery`, `JoinWithSubQuery`, `SelectTopWithoutOrderBy`,
`IncorrectUseLikeInQuery` тощо.

**Підсумок.** Новий `src/core/query/queryLinter.ts` (`lintDocument`/`lintBatch`) —
окремий, НЕблокуючий канал попереджень (`QueryAnalysisResult.warnings`, окремо від
`diagnostics`). Покриття v1: повне з'єднання (`ВСЕ` з обох боків), з'єднання з
вкладеним запитом, `ПЕРВЫЕ N` без `УПОРЯДОЧИТЬ ПО`/`АВТОУПОРЯДОЧИВАНИЕ`, `ПОДОБНО`
з літеральним шаблоном, що починається з неекранованого `%`. Верхньорівневе `ИЛИ` в
`ГДЕ`/`ПО` (аналог `LogicalOrIn*QuerySection`) свідомо відкладено — модель
конструктора представляє умови лише плоским AND-списком, `ИЛИ` існує тільки всередині
непрозорого сирого тексту, а надійного способу виділити межі САМЕ секції `ГДЕ`/САМЕ
умови `ПО` в тексті сьогодні нема (`getBatchStatementSpans` дає діапазон лише на весь
`;`-блок).

У `QueryTextDialog.tsx` (v2, opt-in) попередження показуються окремим бурштиновим
рядком під "✓ Синтаксис корректен" — не приховують і не замінюють цей рядок, кожне
клікабельне (той самий `handleNavigate`, що й панелі «Структура»/«Параметры»).

Ручний прогін по всьому золотому корпусу (1976 запитів): 337 попереджень, 0 винятків
(`top-without-order` — 292, `join-with-subquery` — 31, `full-join` — 9,
`like-leading-wildcard` — 5) — приклади перевірені вручну, ознак хибних спрацювань
не знайдено.

## Відома прогалина, знайдена порівнянням із bsl-parser (не виправлено)

Звірка нашого реєстру віртуальних таблиць з граматикою `1c-syntax/bsl-parser`
знайшла підтверджений критичний баг: `РегистрБухгалтерии.X.Субконто(&Период,
&Условие)` **мовчки втрачає обидва параметри** при циклі розбір→генерація (немає
запису в `accountingPositionKeys` для слайсу `Субконто`). Також 3+ аргументи у
`РегистрРасчета.ДанныеГрафика`/`ФактическийПериодДействия`/`Последовательность.
Границы` потрапляють у загальний `[period, condition]`-фолбек і можуть зміститись.
Не виправлено в межах цієї фази — зафіксовано як наступний кандидат.

## Известные ограничения (не в этой фазе)

- Проверка полей/реквизитов/навигации по-прежнему вне периметра семантического
  валидатора (см. Фаза 8.4 §«Объём и границы» — стандартные поля отсутствуют в
  `MetaTable.fields`, наивная проверка дала бы ложные «Поле не найдено» на каждом
  реальном запросе).
- Полный прогон `validateBatchSemantics` по золотому корпусу (1976 запросов, с
  реальными метаданными) даёт 4 (0.2%) настоящих ложных срабатывания — таблица не
  найдена для `<Тип>.<Объект>.Изменения` (подтаблица регистрации изменений плана
  обмена). Причина: `.Изменения` отсутствует в YAML-кеше метаданных, тот же класс
  пробела, что уже документирован для РегистрРасчета/БизнесПроцесс/Задача (Фаза 8.4).
  Прежде чем оформлять такой прогон в жёсткий CI-гейт, нужно либо исключить
  `.Изменения` по аналогии, либо материализовать её в загрузчике метаданных — само по
  себе не сделано, чтобы не превращать проверку багов в разработку новой функции.
