# Оновлення вікна «Текст запроса» (v2) — ТЗ з урахуванням ризиків

Дата: 2026-09-02.

Мета: модернізувати поточне модальне вікно редагування тексту запиту, додавши інструменти
навігації, аналізу та перевірки, але не змінюючи існуючий механізм формування, збереження
та застосування запиту.

Основний принцип: перший етап — тільки UI/UX та read-only аналіз тексту. Будь-які нові
функції не повинні самостійно змінювати структуру запиту або внутрішню модель конструктора
без явної дії користувача.

**Правило для AI/розробника:** не виконувати масштабний рефакторинг конструктора запитів у
рамках цієї задачі. Змінювати тільки компоненти, безпосередньо необхідні для нового вікна
тексту запиту. Існуючі parser/model/apply механізми повторно використовувати там, де це
можливо. Кожний етап повинен залишати проект у працездатному стані.

## 0. Виявлені ризики та уточнення (перевірено проти поточного коду, 2026-09-02)

Перед стартом роботи звірено з фактичним станом `src/webview` і `src/core/query` — нижче те,
що в чернетці ТЗ було невірним припущенням або пропущеним ризиком. Деталі й правки внесені
в самі пункти нижче (позначено **⚠ Ризик**), тут — короткий підсумок:

1. **Редактор — CodeMirror 6, не Monaco.** `src/webview/components/CodeEditor.tsx` — тонка
   обгортка (157 рядків) майже без розширень (без folding/lint/search/autoclose зараз). П.3
   написаний умовно під Monaco — цього руху немає, весь список фіч п.3 треба мапити на
   CodeMirror-пакети (`@codemirror/lint`, `@codemirror/search`, `@codemirror/language`,
   `@codemirror/autocomplete`). Обсяг — «з нуля», не «не чіпати без потреби».
2. **Один парсер для Apply і для аналізу.** `Применить` вже сьогодні викликає
   `tryOpenBatch(text, resolver, {...})`
   ([ConstructorView.tsx:94](../../../src/webview/components/ConstructorView.tsx#L94)) — той
   самий шлях, що й відкриття існуючого запиту з `.bsl`. Новий `QueryAnalysisService` (п.14)
   МУСИТЬ використовувати саме цей шлях (чи те, що під ним), інакше Structure-панель і
   реальний Apply можуть розійтися в результаті.
3. **Ranges для навігації «структура → код» (п.8) — це не готові дані.** `semanticValidator.ts`
   несе тільки `line`/`col` на діагностику; `queryModel.ts`/`unionModel.ts` не мають
   per-field/per-join source-range взагалі. Прокидання діапазонів через лексер/парсер до
   кожного вузла результату аналізу — реальна робота, не «взяти вже готове у парсера».
4. **«Форматировать» ризикує зачепити семантичні pass'и.** У `src/core/query` вже є
   `qualifyBareFields.ts`, `canonicalizeFieldCasing.ts`, `dropRedundantGroupDerefs.ts` та інші —
   саме ті трансформації (псевдоніми, дедуплікація), які п.5 явно забороняє для форматування.
   Форматер має бути окремим лексичним pretty-printer'ом над токенами, а НЕ проходом через
   існуючий pipeline parse→model→generate (той, що обслуговує Apply).
5. **«Проверить» (кнопка) і дебаунс-аналіз (п.15) повинні бути одним шляхом**, а не двома
   окремими реалізаціями — інакше статус-бар (фоновий) і результат кліку можуть розійтися.
6. **Продуктивність парсера — перевірено, НЕ є проблемою для реальних розмірів запитів.**
   (Виправлення власної попередньої оцінки: 2079ms `corpusRegression.test.ts` — це сумарний час
   на ВЕСЬ корпус із 1976 запитів, а не одного запиту; враженя «парсер повільний» звідси
   неправильне.) Заміряно напряму: найбільший відомий реальний запит у корпусі (485 рядків,
   25 738 символів, `CommonModules-АдресныйКлассификаторСлужебный-Ext-Module.bsl_33.txt`) —
   `parseBatch` ~6 мс, `parseBatch`+`generateBatch` ~15.6 мс. При дебаунсі 300–500 мс це
   ×20–30 запасу. Web Worker можна залишити на пізніший етап, як і планувалось — це підтверджено
   вимірюванням, а не припущенням.
7. **Три шляхи закриття модалки, а в чернетці — два.** Сьогодні закриття відбувається трьома
   шляхами: `×`, клік по backdrop
   ([ConstructorView.tsx:666](../../../src/webview/components/ConstructorView.tsx#L666) —
   закриває без підтвердження вже зараз) і, в новому дизайні, кнопка `Отмена`. Dirty-guard (п.12)
   мусить покривати всі три, не тільки `×`/`Esc`.
8. **Позитив, який важливо не зламати:** текст модалки вже сьогодні живе в ізольованому
   `queryModalText` state (окремо від основної моделі конструктора) і потрапляє в неї лише
   через `dispatch({ type: 'LOAD_BATCH' })` при явному Apply — саме та ізоляція, яку вимагають
   п.1 і п.13. Її не треба вигадувати заново.
9. **CSP webview найімовірніше блокує Web Worker уже сьогодні.** `panel.ts:26` віддає
   `default-src 'none'; script-src 'nonce-…'; style-src …; font-src …` — директив
   `worker-src`/`child-src` немає. За специфікацією CSP3 `worker-src` у такому разі
   відкочується не напряму на `default-src`, а спершу на `child-src`, потім на `script-src`
   (тут це `script-src 'nonce-…'`, без `'unsafe-inline'`/`'strict-dynamic'`) — а виклик
   `new Worker(...)` у рантаймі не може пред'явити nonce (той призначений для `<script>`-тегів),
   тож фактично впирається в заборону так чи інакше. Це технічно ймовірний, а не 100%-но
   верифікований запуском факт (не пробували реально стартувати Worker у цьому webview) — але
   достатньо переконливий, щоб перш ніж переносити аналіз у Worker (навіть у пізнішій фазі),
   явно перевірити й за потреби розширити CSP-рядок у `panel.ts` (`worker-src 'self'` або
   аналог), а не покладатися, що воно «просто запрацює».
10. **`queryHighlight.ts` — пастка для `QueryAnalysisService`.** У webview вже є токенізатор
    для підсвітки (`src/webview/queryHighlight.ts`, підключений через `cmHighlight.ts`), і його
    власний коментар прямо каже: «подсветка чисто косметическая и не обязана бить один-в-один
    с грамматикой». Це НЕ той самий токенізатор, що `src/core/query/sdblLexer.ts`/`sdblParser.ts`
    (реальний парсер, яким керується Apply). Через те що `queryHighlight.ts` уже імпортований у
    webview-шарі й «лежить під рукою», є реальний ризик, що `QueryAnalysisService` для
    Структури/Параметрів помилково побудують на ньому (швидко, «ніби працює») замість
    справжнього `sdblParser`/`semanticValidator` — і отримають саме той розрив
    «Structure ≠ Apply» з п.2, тільки непомітно, з першого ж дня. Explicit заборона: підсвітка
    синтаксису лишається на `queryHighlight.ts`, увесь семантичний аналіз (поля/джойни/умови/
    параметри/діагностика) — тільки через `sdblParser`/`semanticValidator`.
11. **Динамічні розширення CodeMirror (діагностика, пошук) через `Compartment`, не через
    перестворення `EditorView`.** `CodeEditor.tsx` сьогодні перестворює весь `EditorView` (з
    новою `history()`) при зміні `wrapLines`, а зовнішній `value` синхронізує вручну через
    `dispatch`. Якщо результати `analyze()` (лінт-маркери) чи стан пошуку/folding будуть
    оновлюватись так само — через перестворення view чи зміну пропів, що тригерять
    ре-mount, — undo/redo історія буде мовчки скидатись на кожен дебаунс-тік. Це прямо
    порушує вимоги п.4 (undo/redo через history редактора) і п.5 (одна команда Undo повністю
    відкочує форматування). Правильний CodeMirror-патерн: `Compartment` для
    lint-джерела/пошук-стану, оновлення через
    `view.dispatch({ effects: compartment.reconfigure(...) })` — без перестворення `EditorState`.
12. **Пакети CodeMirror: один транзитивний, три відсутні.** `@codemirror/language` вже стоїть у
    `node_modules` (транзитивна залежність через `commands`/`view`), але НЕ прописаний у
    `package.json` — якщо він знадобиться напряму (`bracketMatching()`, `foldGutter()`,
    `codeFolding()`), його треба додати explicit-залежністю, інакше оновлення lock-файлу може
    його прибрати без попередження. `@codemirror/search`, `@codemirror/autocomplete`,
    `@codemirror/lint` відсутні повністю — це нові прямі залежності.
13. **E2e-покриття цього діалогу зараз відсутнє.** `test/e2e/webview.spec.ts` не згадує
    `query-text-editor`/«Текст запроса» жодного разу. Тобто «старий сценарій працює так само» —
    сьогодні критерій, який ніхто автоматично не перевіряє. Див. розділ 21 нижче.

## 1. Поточну поведінку зберегти

Вікно, як і зараз, повинно:

- відкриватися з поточним текстом запиту;
- дозволяти ручне редагування;
- мати кнопку `Применить`;
- при `Применить` викликати той самий існуючий механізм, який використовується зараз
  (`tryOpenBatch` → `dispatch(LOAD_BATCH)`, див. п.0.2);
- мати можливість закрити вікно без застосування змін;
- не змінювати текст запиту до моменту натискання `Применить`.

Не переписувати поточну логіку застосування запиту, якщо для цього немає технічної необхідності.

```
├──────────────────────────────────────────────────────────────┤
│ ↶ ↷ | Форматировать | Проверить | Параметры | Структура | 🔍 │
├───────────────────────────────────────┬──────────────────────┤
│                                       │                      │
│                                       │ Структура запроса    │
│          РЕДАКТОР ЗАПРОСА             │                      │

│                                       │ Соединения           │
│                                       │ Условия              │
│                                       │ Параметры            │
```

## 3. Редактор тексту

**⚠ Ризик (п.0.1):** редактор — CodeMirror 6 (`@codemirror/view`, `@codemirror/state`,
`@codemirror/commands`), Monaco в проєкті немає. Нижче список фіч перекладено на конкретні
CodeMirror-пакети замість «залишити Monaco».

Залишити поточний CodeMirror-редактор (`CodeEditor.tsx`). Додати розширення:

- номери рядків — `@codemirror/view` (`lineNumbers()`);
- syntax highlighting — вже є базово (`cmHighlight.ts`), звірити покриття токенів SDBL;
- поточний рядок — `highlightActiveLine()`;
- виділення парних дужок — `@codemirror/language` (`bracketMatching()`);
- автоматичне закриття `()` — `@codemirror/autocomplete` (`closeBrackets()`);
- горизонтальний та вертикальний scroll — за замовчуванням у CodeMirror;
- folding — `@codemirror/language` (`foldGutter()`, `codeFolding()`);
- стандартні `Ctrl/Cmd+F`, `Ctrl/Cmd+H` — `@codemirror/search` (`search()`,
  `openSearchPanel`/`replaceAll`);
- `Ctrl/Cmd+Z`, `Ctrl/Cmd+Shift+Z` — `@codemirror/commands` (`history()`, `undo`/`redo`);
- `Ctrl/Cmd+A`, `Ctrl/Cmd+C/V/X` — стандартна поведінка браузера/CodeMirror, не чіпати.

Не змінювати стандартну поведінку CodeMirror без необхідності.

**⚠ Ризик (п.0.11):** будь-який стан, що оновлюється динамічно (лінт-діагностика від
`analyze()`, стан search-панелі), підключати через `Compartment` і
`view.dispatch({ effects })`, а не через зміну пропів, що перестворюють `EditorView` —
інакше undo/redo історія скидається на кожне оновлення.

**⚠ Ризик (п.0.12):** `@codemirror/language` — поки транзитивна залежність, не пряма;
`@codemirror/search`, `@codemirror/autocomplete`, `@codemirror/lint` — відсутні, додати в
`package.json` явно перед використанням.

## 4. Toolbar

Перший етап:

```
↶  ↷  | Форматировать | Проверить | Параметры | Структура | Поиск | ⋯
```

Undo / Redo повинні працювати виключно через history редактора (`@codemirror/commands`

## 5. Форматування

Кнопка `Форматировать` форматує лише текст у редакторі. Наприклад:

```
ВЫБРАТЬ
    Контрагенты.Ссылка КАК Ссылка,
    Контрагенты.Наименование КАК email
ИЗ
    Справочник.Контрагенты КАК Контрагенты
ГДЕ
    Контрагенты.Ссылка = &Ссылка
```

**Важлива вимога:** форматування не повинно змінювати семантику запиту. Не допускається:

- зміна псевдонімів;
- зміна JOIN;
- перестановка умов;
- автоматична заміна функцій;
- зміна параметрів;
- оптимізація запиту.

Тільки whitespace, indentation та переноси рядків.

**⚠ Ризик (п.0.4):** `src/core/query` вже містить `qualifyBareFields.ts`,
`canonicalizeFieldCasing.ts`, `dropRedundantGroupDerefs.ts` та інші нормалізуючі pass'и моделі —
саме те, що ця вимога забороняє. **Форматер НЕ повинен ходити через pipeline
parse→model→generate** (той, що обслуговує `tryOpenBatch`/Apply), бо він автоматично підхопить
ці pass'и. Форматер — окремий лексичний pretty-printer над токенами лексера (переноси/відступи
навколо вже наявних токенів), без побудови `QueryModel`.

Перед форматуванням бажано робити snapshot редактора, щоб одна команда `Undo` повністю
відкотила форматування.

## 6. Перевірка запиту

Кнопка `✓ Проверить` перевіряє поточний текст редактора. Результат:

```
✓ Синтаксис корректен
```

або:

```
Ошибка: строка 27, символ 14
Ожидается выражение
```

Помилка повинна відображатися:

- у нижній панелі;
- marker у CodeMirror (`@codemirror/lint`, тип `Diagnostic` з `from`/`to`/`severity`/`message` —
  пакет вже з коробки дає underline + панель + gutter-маркер, підходить майже без доробки);
- клік по помилці переводить курсор на відповідний рядок.

**⚠ Ризик (п.0.5):** ця перевірка та фоновий дебаунс-аналіз (п.15) мають бути ОДНИМ і тим самим
викликом `QueryAnalysisService.analyze()` — кнопка просто форсує негайний виклик замість
очікування дебаунсу. Дві окремі реалізації валідації неприпустимі.

На першому етапі перевірка не повинна змінювати текст.

```

  Ссылка
      Контрагенты.Ссылка

  email
      Контрагенты.Наименование

  password

  firstName
      ЕСТЬNULL(...)

  НастрИнформ
      РегистрСведений.НастройкиИнформирования
```

## 8. Навігація з панелі структури

Клік по `email` повинен перейти до `Контрагенты.Наименование КАК email`.
Клік по `Получатели` — до `ЛЕВОЕ СОЕДИНЕНИЕ Справочник.Получатели КАК Получатели`.
Клік по `&Ссылка` — до `Контрагенты.Ссылка = &Ссылка`.

Реалізувати через offsets/ranges, отримані парсером. Не шукати текст через простий `indexOf`,
якщо вже існує AST або parser model.

**⚠ Ризик (п.0.3):** на 2026-09-02 таких ranges НЕМАЄ в жодному з `queryModel.ts`,
`unionModel.ts`, `semanticValidator.ts` (там лише `line`/`col` на рівні діагностики, не на
рівні кожного поля/джойна/умови). Це означає: перш ніж «навігація структура → код» потрапить
у v1-скоуп як рівноцінний з toolbar/undo пункт, треба окремо оцінити роботу з прокидання
per-node source-range через `sdblLexer`/`sdblParser` до результату `analyze()`. Якщо оцінка
виявиться великою — розглянути вилучення саме навігації (не всієї Структури-панелі) у v1.1.

## 9. Панель параметрів

При натисканні `Параметры` показати список параметрів запиту, наприклад:

```
Параметры запроса

&Ссылка
Предполагаемый тип:
СправочникСсылка.Контрагенты

Использований: 1
```

На першому етапі ця панель повинна бути read-only. Не реалізовувати встановлення значень
параметрів у цьому вікні.

(Примітка: визначення «предполагаемого типу» параметра з умови потребує того ж резолвера
типів полів по джойнах, що вже використовується конструктором — перевірити перевикористання
замість нової реалізації типовиведення.)

## 10. Статусна панель

Внизу редактора:

```
✓ Синтаксис корректен

Строк: 37
Параметров: 1
Источников: 4
Соединений: 3
```

При зміні тексту статус перевірки переходить у:

```
● Есть непроверенные изменения
```

Не можна залишати старе `✓ Синтаксис корректен` після ручної зміни тексту.

## 11. Поведінка `Применить`

Це найважливіша частина для безпечної реалізації. При натисканні `Применить`:

```
1. Отримати поточний текст редактора.

2. Якщо текст не змінювався:
   закрити вікно.

3. Виконати parser/validation (той самий шлях, що й аналіз — див. п.0.2/п.0.5).

4. Якщо критична помилка:
   НЕ закривати вікно.
   Показати помилку.

5. Якщо запит коректний:
   передати текст у поточний існуючий
   механізм Apply (tryOpenBatch → dispatch(LOAD_BATCH)).

6. Якщо Apply успішний:
   закрити вікно.

7. Якщо Apply повернув помилку:
   залишити вікно відкритим.
```

Не робити «text changed → автоматично оновити модель конструктора». Модель оновлюється тільки
після `Применить`.

## 12. Захист від втрати змін

Якщо користувач змінив текст і закриває вікно — показати:

```
Текст запроса был изменен.

Изменения не применены.

[Продолжить редактирование]
[Закрыть без сохранения]
```

Якщо текст не змінений — закривати одразу.

**⚠ Ризик (п.0.7):** цей guard повинен спрацьовувати на ВСІХ шляхах закриття, а не тільки
`×`/`Esc`, названих у чернетці. Зараз їх фактично три:

1. кнопка `×`;
2. клік по backdrop (уже сьогодні закриває без підтвердження —
   [ConstructorView.tsx:666](../../../src/webview/components/ConstructorView.tsx#L666));
3. нова кнопка `Отмена` (якщо трактується як «закрити без застосування», а не як «Esc-синонім
   без diff-перевірки»).

Це також свідома зміна поведінки порівняно з сьогоднішньою (зараз усі три шляхи закривають без
жодного підтвердження) — а не «залишити як є», варто позначити явно в описі задачі виконавцю.

## 13. Dirty state

Після відкриття `originalText` зберігається окремо. Поточне — `editorText`.

```
isDirty = editorText !== originalText;
```

Не визначати dirty через AST або форматований representation. Тільки фактичний текст.

## 14. Parser повинен бути ізольований від UI

Бажана структура:

```
QueryTextDialog
 ├── QueryEditor
 ├── QueryToolbar
 ├── QueryStructurePanel
 ├── QueryDiagnostics
 └── QueryStatusBar
```

Окремий сервіс `QueryAnalysisService`:

```ts
interface QueryAnalysisService {
  analyze(text: string): QueryAnalysisResult;
}

interface QueryAnalysisResult {
  diagnostics: QueryDiagnostic[];
  fields: QueryField[];
  sources: QuerySource[];
  joins: QueryJoin[];
  conditions: QueryCondition[];
  parameters: QueryParameter[];
}
```

UI не повинен знати внутрішню реалізацію parser.

**⚠ Ризик (п.0.2, найважливіший пункт цього ТЗ):** `QueryAnalysisService.analyze()` МУСИТЬ
використовувати той самий парсер/валідатор, що й реальний `Применить`
(`tryOpenBatch`/`sdblParser`/`semanticValidator` — див.
[ConstructorView.tsx:94](../../../src/webview/components/ConstructorView.tsx#L94)), а не окрему
паралельну реалізацію. Інакше Structure-панель і статус-бар можуть показувати результат, що
розходиться з тим, що насправді зробить Apply — довіра до панелі впаде миттєво після першого
такого розбіжного кейсу.

**⚠ Ризик (п.0.10):** окремо від того, ЯКИЙ парсер викликати — не переплутати його з
`src/webview/queryHighlight.ts` (косметичний токенізатор підсвітки, явно документований як
навмисно неточний щодо граматики). `QueryAnalysisService` не повинен імпортувати
`queryHighlight.ts` в жодному вигляді.

**Розміщення в поточній структурі репозиторію** (проєкт уже дотримується чіткого поділу
`src/core/*` — чисті функції без `vscode`/DOM, юніт-тестуються в Node; `src/webview/*` —
React/DOM; `src/extension/*` — vscode-код; див. напр. `resultProcessingTemplate.ts` у
`src/core/query/` як прецедент). Новий код лягає так само, без нової архітектурної схеми:

- `QueryAnalysisService` і форматер (п.5) — `src/core/query/` (напр.
  `queryAnalysisService.ts`, `queryTextFormatter.ts`), поруч із `sdblParser.ts`/
  `sdblGenerator.ts`, яких вони споживають. Без `vscode`/DOM-імпортів, з юніт-тестами в
  `test/unit/` — так само, як усе інше в цій папці.
- `QueryTextDialog`, `QueryEditor`, `QueryToolbar`, `QueryStructurePanel`,
  `QueryDiagnostics`, `QueryStatusBar` — `src/webview/components/`, поруч із вже наявними
  `CodeEditor.tsx`/`ConstructorView.tsx`. `QueryEditor` — це надбудова над існуючим
  `CodeEditor.tsx` (нові розширення з п.3), не заміна його.
- Нових каталогів/пакетів (monorepo-піддиректорій, окремого `workspace` тощо) не потрібно —
  задача лягає у два вже наявні шари без структурних змін верхнього рівня.

## 15. Не блокувати редактор

Парсинг не запускати синхронно на кожен символ. Debounce приблизно 300–500 ms:

```
onChange → dirty = true → debounce → analyze(text)
```

Для дуже великих запитів UI не повинен зависати. Якщо аналіз займає відчутний час, надалі
винести його у Web Worker.

**Перевірено (п.0.6):** заміряно напряму на найбільшому відомому реальному запиті з корпусу
(485 рядків) — `parseBatch` ~6 мс, `parseBatch`+`generateBatch` ~15.6 мс. При дебаунсі
300–500 мс це запас ×20–30. Web Worker дійсно можна лишити на пізніший етап, як і написано
вище — окремо форсувати це в v1 не потрібно (і, відповідно, розширювати CSP `worker-src`
із п.0.9 у v1 теж не треба).

## 16. Захист від race condition

```
analysis #25 стартував
analysis #26 стартував
analysis #26 завершився
analysis #25 завершився
```

Результат `#25` не повинен замінити новіший `#26`. Використати `analysisVersion++` або
cancellation token.

## 17. Помилки parser не повинні ламати редактор

```ts
try {
  analyze();
} catch {
  // ...
}
```

Редактор залишається повністю працездатним. Показати:

```
Не удалось полностью разобрать структуру запроса.
Редактирование текста доступно.
```

`Применить` при цьому має працювати за старими правилами, якщо поточна система дозволяє такий
запит. Це особливо важливо на перших версіях аналізу структури (сам `tryOpenBatch`, що лежить
під `Применить`, — окремий, вже перевірений шлях, і на нього цей `try/catch` не поширюється).

## 18. Backward compatibility

Новий `QueryTextDialog` повинен приймати ті ж основні вхідні дані, які отримує поточний dialog:

```ts
openQueryTextDialog({
  text,
  onApply,
});
```

Можна розширити API опційними полями:

```ts
openQueryTextDialog({
  text,
  onApply,
  metadataProvider?,
  analysisService?,
});
```

Нові залежності повинні бути optional там, де це можливо.

## 19. Feature flag

Додати на перший час `queryTextEditorV2`:

```ts
if (features.queryTextEditorV2) {
  openNewQueryEditor();
} else {
  openLegacyQueryEditor();
}
```

Це дасть можливість швидко відкотити нове вікно без revert великого commit.

## 21. Обов'язкові тести та запобіжники (щоб нічого не зламати)

Мета цього розділу — перетворити «постарайся не зламати» на перевірювані гейти, а не на
довіру до ручного рев'ю.

### 21.1. Файли, яких НЕ торкатись у цій задачі

`sdblParser.ts`, `sdblLexer.ts`, `sdblGenerator.ts`, `semanticValidator.ts`, `queryModel.ts`,
`unionModel.ts`, `metadataResolver.ts`, і сам виклик `tryOpenBatch` у
`handleApplyQueryEdit`. Це — існуючий, вже перевірений корпусом із 1976 запитів контракт.
Нова функціональність тільки СПОЖИВАЄ ці модулі (read-only виклики), нічого в них не змінює.
Якщо в процесі роботи здається, що потрібна зміна в одному з цих файлів — це сигнал зупинитись
і повернутись до обговорення обсягу задачі, а не «трошки поправити по дорозі».

### 21.2. Гейт, який має лишатись зеленим на кожному кроці

Після КОЖНОГО завершеного під-етапу з п.20 (не тільки в кінці всієї задачі):

```
npm run typecheck && npm run test:unit
```

`test:unit` вже включає `corpusRegression.test.ts` (1976 запитів байт-в-байт проти оракула) —
якщо він падає, це означає, що щось зачепило парсер/генератор моделі, а не тільки UI діалогу.
Проект повинен лишатись у працездатному стані на кожному кроці (це вже сказано у преамбулі —
тут це стає конкретною командою, яку реально запускати, а не побажанням).

### 21.3. Нові обов'язкові тести (мають з'явитись РАЗОМ з відповідним кодом, не «потім»)

1. **Формат-тест «форматування не міняє семантику».** Для набору запитів з корпусу (десяток
   репрезентативних, включно з умовами/JOIN/параметрами): `parseBatch(format(text))` дає ту ж
   модель (або той самий `generateBatch`-вивід), що й `parseBatch(text)`. Це прямо перевіряє
   вимогу «форматер міняє тільки whitespace» автоматично, а не на слово.
2. **Тест «однакова відповідь у analyze() і в Apply».** На репрезентативній вибірці з
   `test/fixtures/corpus/golden.jsonl` (десяток-два записів, включно з валідними й свідомо
   невалідними) — не на всіх 1976: фідельність самого парсера на повному корпусі вже покриває
   `corpusRegression.test.ts`, дублювати це тут — зайве навантаження на CI без додаткової
   користі. Перевіряти саме: `QueryAnalysisService.analyze(text)` не показує `✓ синтаксис
   коректний`, якщо `tryOpenBatch(text)` провалюється, і навпаки. Це операціоналізує п.0.2/0.14
   як тест, що реально запускається, а не як дизайн-гайдлайн на віру.
3. **Тест на коректність ranges для навігації.** Фіксований набір рукописних fixture-запитів:
   клік по кожному пункту структури (поле/джерело/join/умова/параметр) повертає range, для
   якого `text.slice(range.start, range.end)` дорівнює очікуваному фрагменту вихідного тексту.
4. **Unit-тести на dirty-state/race-condition логіку** (`isDirty`, `analysisVersion`/cancellation
   token з п.16) — це чиста логіка без DOM/vscode-залежностей, тому мусить жити в `src/core` і
   тестуватись так само, як `resultProcessingTemplate.ts` — без інтеграційного/e2e середовища.
5. **Базовий e2e-тест ПЕРЕД початком переробки, не після.** Сьогодні `test/e2e/webview.spec.ts`
   взагалі не торкається цього діалогу (перевірено — нуль згадок `query-text-editor`/«Текст
   запроса»). Перш ніж міняти компонент, додати мінімальний Playwright-сценарій на ІСНУЮЧУ
   поведінку («Открыть → изменить текст → Применить → модель оновилась», і окремо «Закрыть без
   применения → текст не змінився») — це стане єдиним автоматичним доказом того, що новий
   діалог поводиться так само, як старий, а не лише «за словами».

### 21.4. Rollback

`queryTextEditorV2` (п.19) за замовчуванням `false`, вмикається окремо. Відкат — це переключення
прапорця, а не revert коміту. Прапорець вмикати на `true` за замовчуванням лише після того, як
усі гейти з 21.2–21.3 пройшли і новий e2e-сценарій (21.3.5) зелений і для v2-гілки коду теж.

## Критерії приймання

Зміна вважається готовою, якщо старий сценарій «Открыть текст запроса → изменить текст →
Применить» працює так само, як до рефакторингу. Додатково:

- ✓ текст можна редагувати;
- ✓ undo/redo працює;
- ✓ форматування відкочується через undo;
- ✓ validation не змінює текст;
- ✓ структура оновлюється після зміни тексту;
- ✓ клік по структурі переводить до коду;
- ✓ помилка parser не ламає editor;
- ✓ закриття dirty-вікна запитує підтвердження — на всіх трьох шляхах закриття (`×`, backdrop,
  `Отмена`), не тільки на `×`/`Esc`;
- ✓ Apply при помилці не закриває dialog;
- ✓ старий Apply API (`tryOpenBatch` → `dispatch(LOAD_BATCH)`) не переписаний без необхідності;
- ✓ `QueryAnalysisService.analyze()` і реальний Apply використовують один і той самий
  парсер/валідатор (немає розбіжності між тим, що показує Structure-панель, і тим, що зробить
  Apply);
- ✓ великі запити не блокують UI (перевірено на найбільшому відомому запиті з корпусу — виміряно:
  ~6–16 мс, запас ×20–30 до дебаунсу);
- ✓ `npm run typecheck && npm run test:unit` зелені після кожного під-етапу, не тільки в кінці;
- ✓ жоден з файлів зі списку 21.1 не змінений;
- ✓ додані тести з 21.3 (формат-parity, analyze/Apply-parity, ranges, dirty-state, базовий e2e
  на старій поведінці) присутні й зелені;
- ✓ `queryTextEditorV2` вимкнений за замовчуванням до проходження всіх гейтів.
