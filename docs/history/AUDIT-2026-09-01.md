No production code, public identifiers, or repository structure were changed during the audit.

## Executive Summary

The repository is no longer a thin fork. It is a materially evolved product with:

- a large pure-TS query engine in `src/core/query`;
- a dual-path metadata subsystem with YAML as the primary runtime path and XML parsing as a legacy fallback;
- a React webview with a single large reducer owning plain-query, union, batch, temp-table, and nested-subquery state;
- substantial non-runtime developer infrastructure in `src/cli` and `tooling/` for corpus/oracle validation and UI parity research.

The current codebase is functional enough to build, package, and pass most tests, but the baseline is not green:

- extension/core/CLI TypeScript check passes;
- webview TypeScript check fails;
- unit tests fail on a hidden `src/cf` path dependency;
- E2E tests fail in 3 higher-complexity multi-query flows;
- packaging succeeds and the VSIX is internally coherent;
- production dependency audit is clean.

The main migration blockers are not dead code. They are safety-net gaps, webview/state complexity, and missing CI verification for the paths most likely to break during structural moves.

## PASS 2: Actual Architecture & Risks

### Actual Runtime Architecture

1. Extension activation
   - `package.json` contributes commands and context menu entries.
   - `src/extension/extension.ts` activates by command contribution, creates an output channel, resolves the active query at cursor, and opens the webview.

2. Extension host orchestration
   - `src/extension/panel.ts` owns HTML/CSP generation, webview creation, metadata loading, YAML-vs-XML fallback logic, message dispatch, cache refresh, and final editor insertion/disposal.

3. Metadata subsystem
   - primary runtime path: `parseConfiguration()` writes YAML tree to `queryConsole.parserOutputPath`, `loadMetadataCached()` loads/rebuilds `model-cache.json`, then supplies `MetaTable[]`.
   - fallback runtime path: direct XML parse via `parseCf()` plus cache in `context.globalStorageUri`.
   - discovery path: `resolveCfPath()` prefers explicit config, then `<workspace>/src/cf`, then breadth-first `Configuration.xml` search.

4. Query engine
   - `src/core/query/sdblParser.ts` parses text into model/doc structures.
   - `src/core/query/sdblGenerator.ts` generates canonical SDBL from model/doc structures.
   - transformations and validators in sibling files implement normalization, semantic validation, star expansion, deref cleanup, comment binding, and batch handling.

5. Webview
   - `src/webview/App.tsx` is the host-side React root for message handling, load/validation state, and final `ConstructorView`.
   - `src/webview/components/ConstructorView.tsx` composes tabs, dialogs, side strips, nested subquery constructor, and query preview flows.
   - `src/webview/state/queryStore.ts` owns almost all interactive state and reducer logic.

6. Shared boundary
   - `src/shared/messages.ts` defines the entire host/webview protocol.
   - `src/webview/bridge.ts` is a thin transport adapter over `acquireVsCodeApi()` and `window.message`.

### Actual Dependency Boundaries

Observed boundaries are mostly sensible:

- `src/core/*` stays free of VS Code and React.
- `src/shared/messages.ts` imports core types, so the protocol depends on both metadata and query model shapes.
- webview imports core types and runtime helpers directly, not through an intermediate application layer.
- extension imports core runtime logic directly and orchestrates it itself.

There is no evidence that a generic `application/` layer is missing by principle. The real issue is concentration of orchestration in a few hotspots.

### Critical Hotspots

Measured hotspots:

- `src/webview/state/queryStore.ts`: `2029` LOC
- `src/core/query/sdblParser.ts`: `5108` LOC
- `src/core/query/sdblGenerator.ts`: `3160` LOC
- `src/extension/panel.ts`: `205` LOC but with mixed responsibilities

Interpretation:

- `sdblParser.ts` and `sdblGenerator.ts` are large, but they are also the canonical query engine and heavily tested. Size alone is not enough evidence to split them.
- `queryStore.ts` is large and also mixes several state domains: single query, union participants, batch queries, synthetic temp-table/subquery metadata, focus state, and nested modal interactions.
- `panel.ts` mixes concerns that would complicate safe incremental structural work: panel lifecycle, resource paths, metadata cache strategy, and message protocol handling.

### Message Protocol

The host/webview protocol is small and typed:

- Host -> webview:
  - `init`
  - `metadataTree`
  - `refFields`
  - `generatedText`
  - `refreshResult`
  - `loadModel`
- Webview -> host:
  - `ready`
  - `expandRef`
  - `generate`
  - `insertText`
  - `cancel`
  - `refreshCache`

Strengths:

- single shared union types in `src/shared/messages.ts`
- one transport adapter in `src/webview/bridge.ts`
- no evidence of string drift between sender and receiver

Risks:

- protocol payloads embed core types directly, so large model refactors would ripple through the boundary
- handling in `panel.ts` is a linear `if/else` chain rather than an exhaustively checked dispatcher

## Final Conclusions

The repository is already organized around the right big domains:

- metadata
- query engine
- extension host
- webview
- shared contracts
- tooling/test infrastructure

The next step is not a broad directory redesign. The safest next step is to repair the baseline and then refactor around proven hotspots:

1. safety net first;
2. extension/webview orchestration boundaries second;
3. large query-engine internals only if truly necessary.

That path preserves current behavior, respects the real compatibility boundaries, and gives structural migration a meaningful chance of succeeding without breaking Query Console 1C.

  the actual import graph: `sdblGenerator.ts` ↔ `exprFormatter.ts`, and `sdblParser.ts`
