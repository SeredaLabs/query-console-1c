# Дорожная карта

Статус: **операционный документ**. Приоритет проекта -- стабилизация ядра перед
новыми UI-возможностями. Полный перечень подтверждённых дефектов -- в
[KNOWN_ISSUES.md](KNOWN_ISSUES.md), границы безопасного поведения -- в
[CORE_LIMITATIONS.md](CORE_LIMITATIONS.md).

## Текущая цель: стабилизация ядра

### 1. Сохранить данные при round-trip SDBL

- ✅ `РегистрБухгалтерии.*.Субконто(...)` и позиционный аргумент `ВидыСубконто`
  у `Остатки`/`Обороты`/`ОборотыДтКт`/`ОстаткиИОбороты` -- исправлено (PR-04),
  regression-тесты добавлены (`virtualTableRoundTrip.test.ts`,
  `accountingVirtualParams.test.ts`).
- ✅ Формы с тремя и более аргументами (`РегистрРасчета.*.ДанныеГрафика`,
  `ФактическийПериодДействия`, `Последовательность.*.Границы`) остаются lossy --
  настоящая раскладка параметров неизвестна, чинить вслепую нельзя (см.
  KNOWN_ISSUES.md). Apply-blocking реализован (PR-05, ТЗ §54 P0.5): парсер
  помечает `VirtualParams.unsafeExtraArgs`, `findUnsafeVirtualTables`
  (`semanticValidator.ts`) находит такие источники рекурсивно (включая
  подзапросы), кнопка «ОК» в App.tsx блокируется до записи в редактор --
  сам parse/generate по-прежнему теряет 3-й+ аргумент, но конструктор больше не
  может молча применить такую модель. Открытие/просмотр текста в конструкторе
  НЕ блокируется -- только запись (см. `findUnsafeVirtualTables` в
  `semanticValidator.ts`). Regression-тесты: `virtualTableRoundTrip.test.ts`,
  `semanticValidator.test.ts`, `webview.spec.ts` (e2e).

### 2. Разделить tolerant parsing и strict validation

- Не позволять `custom`-fallback маскировать синтаксические ошибки при «Применить».
- Выбрать и интегрировать strict expression validator или независимый SDBL grammar oracle.
- Сделать проверку воспроизводимой в CI, а не только локальной через необязательный
  tree-sitter WASM.

### 3. Сделать импорт метаданных надёжным

- ✅ Парсить во временный каталог и атомарно публиковать результат только после
  приемлемой валидации (staged build + logical commit + ownership guard,
  `src/core/metadata/parser/generationStore.ts`).
- ✅ Показывать пропущенные XML и причину, а не выдавать частичную модель за
  успешную (`MetadataBuildIssue[]`, поверхностно выводится в output channel).
- ⬜ Выявлять устаревший cache относительно XML-выгрузки или явно сообщать о нём
  (сейчас только `fs.existsSync` — не сравнивается с mtime исходного XML).

### 4. Закрыть integration gap

- Добавить Extension Host тесты для регистрации команд, message bridge, загрузки
  metadata и вставки/замены BSL-литерала.
- Оставить Playwright webview harness как UI-уровень, но не считать его проверкой
  интеграции с VS Code.

## Завершённые этапы

Базовый продукт уже имеет XML metadata parser, визуальный конструктор, генерацию и
обратный разбор SDBL, пакетные запросы, комментарии, локальную проверку
существования таблиц и opt-in редактор текста v2. Подробные фазовые отчёты и
исследовательские материалы сохранены в [history/](history/README.md); они не
определяют текущие приоритеты.

## Неизменные архитектурные решения

- `src/core` остаётся pure TypeScript и не зависит от VS Code или React.
- `QueryModel` -- общая модель parser, generator и webview.
- YAML -- проверяемый промежуточный артефакт metadata parser, а не первичный источник.
- Контракт host ↔ webview сосредоточен в `src/shared/messages.ts`.

Подробная карта зависимостей: [ARCHITECTURE.md](ARCHITECTURE.md).
