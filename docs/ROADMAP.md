# Дорожная карта

Статус: **операционный документ**. Приоритет проекта -- стабилизация ядра перед
новыми UI-возможностями. Полный перечень подтверждённых дефектов -- в
[KNOWN_ISSUES.md](KNOWN_ISSUES.md), границы безопасного поведения -- в
[CORE_LIMITATIONS.md](CORE_LIMITATIONS.md).

## Текущая цель: стабилизация ядра

### 1. Сохранить данные при round-trip SDBL

- ✅ `РегистрБухгалтерии.*.Субконто(...)` и позиционный аргумент `ВидыСубконто`
  у `Остатки`/`Обороты`/`ОборотыДтКт`/`ОстаткиИОбороты` -- исправлено (PR-04),
  regression-тесты добавлены (`virtualTableRoundTrip.test.ts`,
  `accountingVirtualParams.test.ts`).
- ✅ Формы с тремя и более аргументами (`РегистрРасчета.*.ДанныеГрафика`,
  `ФактическийПериодДействия`, `Последовательность.*.Границы`) остаются lossy --
  настоящая раскладка параметров неизвестна, чинить вслепую нельзя (см.
  KNOWN_ISSUES.md). Apply-blocking реализован (PR-05, ТЗ §54 P0.5): парсер
  помечает `VirtualParams.unsafeExtraArgs`, `findUnsafeVirtualTables`
  (`semanticValidator.ts`) находит такие источники рекурсивно (включая
  подзапросы), кнопка «ОК» в App.tsx блокируется до записи в редактор --
  сам parse/generate по-прежнему теряет 3-й+ аргумент, но конструктор больше не
  может молча применить такую модель. Открытие/просмотр текста в конструкторе
  НЕ блокируется -- только запись (см. `findUnsafeVirtualTables` в
  `semanticValidator.ts`). Regression-тесты: `virtualTableRoundTrip.test.ts`,
  `semanticValidator.test.ts`, `webview.spec.ts` (e2e).

### 2. Разделить tolerant parsing и strict validation (PR-14, ТЗ §56 P1.8 SPIKE) -- отложено

- Не позволять `custom`-fallback маскировать синтаксические ошибки при «Применить».
- Выбрать и интегрировать strict expression validator или независимый SDBL grammar oracle.
- Сделать проверку воспроизводимой в CI, а не только локальной через необязательный
  tree-sitter WASM.

SPIKE-сравнение вариантов (ТЗ §20), сделанное без реализации -- решение
"когда делать" осознанно отложено:

| Вариант | Состояние |
|---|---|
| Внешняя грамматика (tree-sitter-sdbl) | Инфраструктура уже есть (`test/helpers/assertValidSdbl.ts`, `tooling/scripts/build-wasm.sh`), но нерабочая в обычном окружении -- нужен отдельный репозиторий-источник грамматики (`tmp/tree-sitter-bsl`, не в этом репо), CLI `tree-sitter` и `emscripten`. Оракул сейчас молча no-op'ает везде, где вызывается (`sdblGrammarAvailable` false). |
| Более строгий текущий парсер | `ParseOptions` (`sdblParser.ts`) не имеет НИ ОДНОГО флага строгости сейчас -- это была бы настоящая новая работа: явный запрет `custom`-fallback для синтаксически невалидных выражений при «Применить» (та же проблема, что названа критической №1 в `KNOWN_ISSUES.md`). Не требует новых зависимостей. |
| Независимый grammar oracle (третья сторона) | Не исследован. |

Предварительная рекомендация (не решение): вариант "более строгий текущий
парсер" -- не требует недоступного тулчейна, согласуется с "smallest safe
change". Внешняя грамматика остаётся задокументированной альтернативой на
случай появления нужной инфраструктуры.

### 3. Сделать импорт метаданных надёжным

- ✅ Парсить во временный каталог и атомарно публиковать результат только после
  приемлемой валидации (staged build + logical commit + ownership guard,
  `src/core/metadata/parser/generationStore.ts`).
- ✅ Показывать пропущенные XML и причину, а не выдавать частичную модель за
  успешную (`MetadataBuildIssue[]`, поверхностно выводится в output channel).
- ✅ Выявлять устаревший cache относительно XML-выгрузки -- решено ПОБОЧНО
  через PR-10 widen: основной путь (`loadMetadataSnapshotFirst`) сравнивает
  mtime закоммиченного снимка с mtime XML в 17 распознаваемых подкаталогах
  (`newestRelevantMtime`) и делает rebuild при более новом XML, вместо тихой
  выдачи устаревших данных. Подтверждено вручную на двух реальных
  конфигурациях. Остаточный узкий случай (отдельная YAML-only ветка,
  `fs.existsSync` без сравнения mtime) описан в KNOWN_ISSUES.md -- она
  задействуется только когда `cfPath` не задан или когда И direct-путь, И его
  YAML-откат оба упали.

### 4. Закрыть integration gap

- Добавить Extension Host тесты для регистрации команд, message bridge, загрузки

- Оставить Playwright webview harness как UI-уровень, но не считать его проверкой

### 5. Прямой JSON-снимок метаданных (ТЗ §55 P1.2-P1.4, PR-08/09/10 -- сделано)

- ✅ Прямой путь XML → JSON (без YAML) реализован
  (`src/core/metadata/parser/snapshotBuilder.ts`) и провалидирован на ДВУХ
  независимых реальных конфигурациях пользователя (не в репозитории) --
  холодная сборка в 1.6-1.9 раза быстрее существующего YAML-пути, 0
  расхождений в итоговой модели. Dual-path fallback на существующий YAML-путь
  при любом сбое direct-пути реализован (`src/core/metadata/parser/loadMetadataSafe.ts`).
- ✅ Production switch (PR-10) СДЕЛАН и расширен: `panel.ts` использует
  `loadMetadataSnapshotFirst`/`loadMetadataWithFallback` как основной путь для
  ЛЮБОГО заданного `cfPath` -- первое открытие, повторное открытие уже
  существующего YAML-пользователя, и «Обновить кэш» (`refreshCache`). YAML
  остаётся только как: (1) внутренний fallback при сбое direct-пути,
  (2) отдельная ветка `loadMetadataCached`, когда `cfPath` не задан или упали
  ОБА пути сразу. Подробности и цифры -- `docs/PERFORMANCE_BASELINE.md`.
- ⬜ CONDITIONAL, отдельная реализация: параллелизация XML-парсинга через
  `worker_threads`. Замерено эмпирически (не теоретически): 98% времени
  холодной сборки уходит на сам XML-парсинг (`@xmldom/xmldom`, ~1.5 мс/файл);
  4-6 воркеров дают ещё ~1.9x поверх уже достигнутого -- совокупно около
  ~3x против оригинального YAML-пути. НЕ реализовывать без отдельного решения:
  нужна отдельная точка сборки для esbuild (сейчас всё расширение собирается
  одним файлом), обработка ошибок/падений воркеров, новые тесты -- и выигрыш
  касается только холодной сборки (тёплая загрузка уже быстрая, ~10-50 мс).
  Цифры по количеству воркеров -- `docs/PERFORMANCE_BASELINE.md`.
- SQLite как формат снимка -- измерено и отклонено (медленнее на запись,
  больше на диске, не даёт выигрыша для нашего паттерна доступа "читаем всю
  модель разом"); см. `docs/PERFORMANCE_BASELINE.md`.

## Что осталось (консолидированный список, 2026-09-05)

Всё нижеперечисленное -- осознанно отложенные пункты, не автономное
продолжение. Каждый требует отдельного решения "когда" и "кто начинает".

1. **PR-11/12 (удаление YAML/legacy runtime)** -- заблокировано ТЗ §62/§63
   Definition of Done: "production consumers больше не требуют YAML-путь"
   пока НЕ верно -- YAML остаётся fallback-сетью безопасности (см. п.5) и
   единственным путём для узкого набора случаев. Разблокируется не кодом, а
   временем реального использования без инцидентов (не календарным сроком --
   ТЗ §61 явно запрещает произвольные временные пороги).
2. **PR-14 (Strict Syntax Validation)** -- SPIKE сделан (см. п.2 выше,
   сравнение вариантов), реализация осознанно отложена пользователем.
3. **Extension Host integration-тесты** (п.4) -- не начаты; `panel.ts` до сих
   пор не имеет автоматизированного покрытия (все проверки этой сессии --
   ручные smoke-тесты + существующие unit/e2e на нижних слоях).
4. **Worker-threads параллелизация XML-парсинга** (п.5, CONDITIONAL) --
   измерено (~1.9x дополнительно к уже достигнутому), не реализовано;
   требует отдельной точки сборки esbuild и обработки ошибок воркеров.
5. **Остаточный узкий case устаревшего кэша** (п.3) -- отдельная
   `loadMetadataCached`-ветка без сравнения mtime; затрагивает только
   редкий сценарий (нет `cfPath`, либо оба пути метаданных упали разом).
6. **"После стабилизации"** -- локализация, расширение семантической
   проверки, функциональные расширения конструктора (см. ниже) -- по
   определению начинаются только после того, как пункты 1-3 выше закрыты
   или явно признаны неприоритетными.

## Завершённые этапы

Базовый продукт уже имеет XML metadata parser, визуальный конструктор, генерацию и
обратный разбор SDBL, пакетные запросы, комментарии, локальную проверку
существования таблиц и opt-in редактор текста v2. Подробные фазовые отчёты и
исследовательские материалы сохранены в [history/](history/README.md); они не
определяют текущие приоритеты.

## Неизменные архитектурные решения

- `src/core` остаётся pure TypeScript и не зависит от VS Code или React.
- `QueryModel` -- общая модель parser, generator и webview.
- YAML -- проверяемый промежуточный артефакт metadata parser, а не первичный источник.
- Контракт host ↔ webview сосредоточен в `src/shared/messages.ts`.

Подробная карта зависимостей: [ARCHITECTURE.md](ARCHITECTURE.md).
