# C11 slot audit — stopped before implementation, 2026-09-29

Historical audit: the subsequently authorized [C12 fix](c12-characteristics-eof-2026-09-29.md)
closes the parser data-loss finding. C11 remains OPEN.

Baseline: `9843b3b` / `v0.1.93`. The requested step 4 was stopped by its explicit
conditions: an Apply path loses source content, and correcting the loss requires
changing the parser rather than only `findMalformedCustomExpressions`.
No production code or test expectations were changed.

## Current static coverage

The shared Classic/Canvas gate calls `findMalformedCustomExpressions` on the
assembled model. Existing expression checks use `isStructurallyValidExpression`;
these are structural checks, not complete platform validation.

| Slot | Current coverage / boundary |
|---|---|
| WHERE / HAVING custom expressions | `expression` and `leftExpr` checked only when `custom` is true; condition subqueries traversed recursively. |
| Non-custom condition operands | `param` is not checked; `leftExpr` outside the custom branch is not checked. Operator context matters: a BETWEEN right-hand side is not an independent expression. |
| JOIN | Legacy custom `join.expression` and custom conjunct expressions checked. Structured operands are field references. |
| SELECT and trailing fields | `expression` checked; the dedicated `parseEmptyTableColumns` exception recognizes the select-only `ПУСТАЯТАБЛИЦА.(…)` syntax. |
| Tabular-section projection | Expression columns and legacy `exprFields` checked; `castPrefix` is not checked. Named columns are references. |
| GROUP BY / grouping sets | Expression fields checked in both collections. The aggregate list supplies aggregate selection metadata; it is not traversed separately. |
| ORDER / totals | Expression fields checked in order, total groups and total values. |
| INDEX BY | Every index field's expression checked. |
| Report-builder `{…}` blocks | `ref` checked only for `condition` rows, in all four collections. Ordinary refs are parsed segment by segment; manually constructed model values have no separate static check. |
| Virtual-table arguments | No traversal of `VirtualParams` strings. This includes periods, conditions, periodicity/fill method, accounting filters, subconto types, order/top and calculation-register dimension/section arguments. |
| `accountingArgs` | Transient parser remapping data, removed from final parsed models; generator uses named VirtualParams slots. It is not a separate rendered argument list. |
| Characteristics block | Entire raw `model.characteristics` is unchecked. It is a section, not an ordinary expression. Missing closing `}` can erase the text before this gate (C12 below). |
| Nested queries | Source and condition QueryDocument subqueries are traversed, including their UNION members; all batch documents are traversed. Opaque subquery text retains the expression acceptor's existing balance-only limitation. |

A corpus sweep found 0 existing malformed hits in each metadata mode. Only six
nonempty `virtual.period` and seven `virtual.condition` values occur per mode;
there are no characteristics blocks. Therefore a zero-new-blocker corpus gate
alone would not establish compatibility for the specialized argument syntax.

The existing expression acceptor rejects `{(Код = &Код) КАК Отбор}`, while the
current parser/generator and Apply accept it as a DCS virtual-table argument.
Blindly checking every VirtualParams string as a standalone expression would
introduce a rejection. This is a compatibility observation, not a new live 1C
validity claim. Existing template-marker exceptions also remain part of the
acceptor's contract and require explicit consideration.

## C11 reproduction: missing virtual-table check

Input:

```sdbl
ВЫБРАТЬ Т.Период
ИЗ РегистрСведений.Курсы.СрезПоследних(, Код = = &Код) КАК Т
```

`findStaticApplyBlocker` returns `null`. The expression acceptor correctly rejects
`Код = = &Код`, but this slot is never passed to it. `decideApply` returns
`{ ok: true }`: this structural error is not caught even by the generated-text
reparse. Lexical errors such as a bare `&` are a different case; final parsing can
catch them, but static coverage is still missing.

## C12 reproduction: input disappears before the static gate

Input (intentionally missing only the closing brace):

```sdbl
ВЫБРАТЬ 1 КАК Число {ХАРАКТЕРИСТИКИ ТИП(Справочник.Валюты)
```

Verified both without metadata and with the committed YAML resolver through
`tryOpenBatch(input, resolver, { preserveComments: true })` → `LOAD_BATCH` →
`computeBatchTextSafe` → the shared Apply gate:

- opening succeeds;
- `model.characteristics === ''`;
- `findStaticApplyBlocker` returns `null`;
- generated output is only `ВЫБРАТЬ\n\t1 КАК Число`;
- `decideApply` returns `{ ok: true }`.

In `sdblParser.ts` the characteristics reader initializes `end = open.pos` and
breaks on EOF without requiring the outer brace to close. The final slice is
empty. The valid closed-block control preserves the block and allows Apply.
C10's store preservation cannot recover text already discarded by the parser.

The narrow proposed prerequisite is to reject EOF before the closing
characteristics brace when opening/parsing, with a regression proving the input
cannot reach Apply. This requires an explicit exception to the step's parser
restriction. It does not require recovery, commentBinder or C8 changes.

for step 4. Full release gates and a HEAD/worktree generation comparison were not
