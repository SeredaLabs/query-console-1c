# C9 — preserve HAVING through the webview store

Baseline: `140985e` (A1 lexical contract). The parser and generator already retain
`QueryModel.having`, but `modelToFlat` / `buildModelFromFlat` omitted it. Merely
loading and saving a query through Classic or Canvas could therefore remove its
HAVING filter, including queries with GROUP BY.

## Change and boundaries

`SavedQuery` and `QueryState` now have optional `having: Condition[]` fields.
The existing conversion, `snapshotActive` and `restoreSaved` functions carry the
field. New/older snapshots without HAVING restore `undefined`, clearing any
previous active HAVING instead of leaking it across queries. No new persistence
version is needed; missing optional values retain the previous no-HAVING behavior.

Production changes are confined to `src/webview/state/queryStore.ts` and
`src/webview/state/queryStore/snapshots.ts`. No parser/generator change, HAVING
editor, source-renaming behavior or unrelated store refactor is included.
Existing Apply validation now sees retained malformed HAVING and refuses it.

## Regression evidence

- `queryStore.having.test.ts`: ten cases cover conversion/reopening, aggregate
  HAVING without GROUP BY, a condition subquery, unrelated field-alias edits,
  UNION and batch switching, creation without value leakage, loading a plain
  query, older snapshots and malformed-HAVING Apply refusal.
- The first nine cases reproduced eight failures before the fix; the no-HAVING
  load case already passed. All pass after the fix. The older-snapshot case was
  then added and verified.
- The seven HAVING cases in `expressionLexicalFailure.test.ts` now exercise
  top-level HAVING through the store directly, removing the A1 test workaround.
- Two browser regressions in `canvas.spec.ts` exercise Classic and Canvas:
  load HAVING → edit an unrelated SELECT alias → Save → inspect retained HAVING
  → reopen → save identical output.

## Corpus impact

A temporary before/after sweep over `LOAD_BATCH → assembleBatch → generateBatch`
used all 1976 committed queries, both without metadata and with the committed YAML
resolver. **33 queries change in each mode**. All changes are restored HAVING:
removing top-level HAVING from the new models reproduces the old output exactly
for every changed query. **Zero unexplained changes or probe exceptions.**

Representative cases:

| Corpus file | Before store fix | After store fix |
|---|---|---|
| `Catalogs-ГруппыДоступа-Ext-ManagerModule.bsl_11.txt` | HAVING absent | Retains `СУММА(Данные.ВидИзмененияСтроки) <> 0` |
| `Catalogs-ГруппыДоступа-Ext-ManagerModule.bsl_8.txt` | HAVING absent | Retains the same aggregate filter |
| `Catalogs-ПроизводственныеКалендари-Ext-ManagerModule.bsl_1.txt` | HAVING absent | Retains `МАКСИМУМ(ДанныеПроизводственногоКалендаря.Дата) ЕСТЬ НЕ NULL` |

The core parse/generate golden contract is unchanged. No snapshots, golden files,
fixtures or classification baselines were updated. This is recorded corpus
evidence, not fresh live-platform validation; the optional tree-sitter WASM oracle
remains unavailable.
