# A1.4 — token-backed tuple closing-parenthesis search

Historical slice report. Its raw-fallback policy was subsequently replaced by
the [expression lexical contract](../expression-lexical-contract.md).

Baseline: `5b84c1b` plus the uncommitted A1.3 slice. A1.3 changes were preserved;
all before/after comparisons below isolate A1.4 against that working-tree state.

## Scope and behavior

`moveNotBeforeTuple` in `sdblGenerator.ts` now locates the closing parenthesis
of its leading tuple using lexer punctuation and source positions. Its sole
caller, `buildConditionStrings`, handles custom WHERE/HAVING expressions.
The first-character guard, comma detection, case-sensitive `НЕ В` matching,
whitespace rules and source slicing remain unchanged. Lexer failure anywhere,
including after the tuple, uses the former character search (`findTupleCloseRaw`).
The main helper is exported for tests, following the preceding A1 slices.

Direct helper changes: parentheses inside date tokens and line comments are no
longer mistaken for tuple boundaries. For example, `('(', Б) НЕ В (&П)` now
becomes `НЕ ('(', Б) В (&П)`; `(А, // )\nБ) НЕ В (&П)` moves NOT while retaining
the tuple text and comment verbatim. These are lexical robustness examples,
not platform-valid date claims or a new end-to-end comment-preservation promise.
Downstream condition formatting already normalizes these representative cases;
the production probes below found no output changes.

No parser, Apply, other scanner, AST, dependency or persisted format changes.
A1 remains open. The next scanner is a separate task.
